# DAG + Agent SDK 入門メモ（直列パイプライン経験者向け）

> 作成: 2026-04-04
> 対象: 直列パイプラインしか作ったことがない初心者エンジニア
> 目的: 「将来ループ・追加工程が増える」前提で、安全に設計を始めるための最短ガイド

---

## 1. なぜ直列からDAGへ移るのか

直列パイプラインは次の形で、最初は簡単。

```
書き起こし -> 修正 -> 翻訳 -> 字幕化
```

ただし、次の要求が出ると急に辛くなる。

- 翻訳後に意味近似チェックして、NGなら翻訳へ戻す
- 用語漏れチェックして、NGなら再翻訳する
- 書き起こしを2系統で実行して差分チェックする

この時点で構造は「1本道」ではなく「分岐・合流・再実行」になる。
このため、工程をノードとして扱うDAG設計へ移る。

---

## 2. 重要用語（最小）

- `Node`: 1つの工程（例: translate, semantic_check）
- `Edge`: 次へ進む条件（例: score >= 0.85）
- `RunState`: 実行中の全記録（入力/出力/メトリクス/試行回数/エラー）
- `Policy`: 再試行・分岐ルール（例: 最大3回まで再翻訳）

---

## 3. Agent SDKの役割

Agent SDKは有効だが、役割分離が必要。

- LLMに任せる: 翻訳・言い換え・修正案生成
- ツールで決定論にする: CPS計算、文字数制約、用語漏れ判定、閾値判定

原則:

```
LLM = 生成担当
Tool = 判定担当
Policy = 再実行判断
```

---

## 4. 典型ワークフロー（例）

```
transcribe_primary
  -> transcribe_checker
  -> asr_consensus_check
     -> (NG) human_flag
     -> (OK) ja_correct
  -> translate
  -> semantic_check
     -> (NG) translate に戻す
  -> terminology_check
     -> (NG) translate に戻す
  -> subtitle_format
  -> cps_guard
     -> (NG) subtitle_format に戻す
  -> done
```

---

## 5. 利点と欠点

利点:

- 工程追加がしやすい（ノード追加で拡張）
- ループ条件を明示できる（品質担保しやすい）
- 実験しやすい（API A/B比較、ローカル/クラウド比較）
- 失敗解析がしやすい（どのノードで止まったか追跡可能）

欠点:

- 初期実装コストが上がる
- 設計理解に学習コストが必要
- 分岐/ループが増えると実行経路の把握が難しくなる
- 早期段階で作り込みすぎると過設計になる

---

## 6. 過設計を防ぐ進め方（推奨）

1. まずDAG上で直列と同じ4工程だけ動かす
2. 次に翻訳意味チェックノードを追加
3. 次に用語漏れチェックノードを追加
4. 最後にASRダブルチェックを追加

この順にすると「将来拡張性」を維持しつつ、開発速度を落としにくい。

---

## 7. 実装時チェックリスト

- 全ノードで入力/出力スキーマを固定したか
- ループに最大試行回数と停止条件を入れたか
- LLM判定に依存せず、ツールの決定論チェックがあるか
- `RunState` に再現に必要な情報（provider/model/tokens/errors）が残るか
- UIレポートから各ノード結果を確認できるか

---

## 8. 本プロジェクトへの適用方針（2026-04-04時点）

- 全体制御: DAG実行エンジン
- ノード内自動化: Agent SDK
- 既存PoC (`poc/step2_pipeline`) はノード実装資産として流用
- フロントはDrop-First UXを維持し、バックエンドのみ段階的に差し替え
